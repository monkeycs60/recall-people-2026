# Encrypted Sync and Onboarding Refresh Design

## Context

Recall People currently stores contacts, notes, groups, and follow-up events in local SQLite. This supports the privacy promise, but creates a severe product risk: if a user deletes the app, loses their phone, or signs in on another device, their relationship memory does not come back.

The next version should introduce encrypted backup/sync and refresh onboarding so users understand the product value quickly. The onboarding should stop ending with a passive privacy explanation. Instead, it should end with a privacy-led action: enable encrypted backup.

## Product Direction

The onboarding story should be value-first:

1. Choose language.
2. Remember everyone you meet.
3. Turn notes into a useful contact profile.
4. See upcoming moments in your contacts' lives.
5. Ask your network anything.
6. Because privacy matters, enable encrypted backup.

The previous privacy/AI explanation should move to Profile as a lower-hierarchy modal or sheet. It remains accessible for transparency and App Store review, but it should not be the final onboarding moment.

## Encrypted Backup Model

Use a user-controlled recovery phrase, generated by Recall People, with English words.

The model is:

- The user must be logged in to a Recall People account.
- The app generates a short recovery phrase, for example `sun-river-cobalt-47`.
- The app uses that phrase to derive a key locally.
- Contact data is encrypted on-device before upload.
- The backend stores only encrypted backup data tied to the account.
- Recall People cannot read or decrypt the user's contacts.
- On a new phone, the user logs in and enters the recovery phrase to restore.

This is not a strict password flow. Do not impose complex password rules. The phrase is generated by the app so it can be easy to type while still safer than a 6-digit OTP.

Provide recovery phrase actions:

- Copy.
- Download/save.
- Send to email, with a short warning that email storage is outside Recall People's encryption.

## Profile Placement

Add a data/privacy area in Profile:

- `Encrypted backup`: status, setup, recovery phrase actions, restore flow.
- `Privacy & AI processing`: opens the existing detailed privacy/AI explanation currently represented by legal/AI consent content.
- Keep `Export data`.

The backup row should live in the Data section, above export. It should show status:

- `Not enabled`
- `Last backup today`
- `Needs recovery phrase`
- `Sync failed`

## Landing Page Update

The landing page should mention encrypted backup and local-first privacy without turning the hero into a security page.

Recommended sections to update:

- Feature section: add `Encrypted backup with your recovery phrase`.
- Privacy/trust section: clarify `Your contacts are stored locally. Backups are encrypted before they reach our servers.`
- Product visuals: use the same generated mockup family as onboarding: useful profile, upcoming calendar, assistant answer, encrypted backup.

## Visual Direction

Use generated in-app-style mockups rather than direct screenshots.

Style constraints:

- Match Recall colors and typography feel.
- Use warm light backgrounds with purple accents.
- Show concrete product UI: cards, rows, calendar entries, assistant bubbles, locked backup.
- Use the same flat avatar/illustration language already present in the app.
- Avoid generic corporate illustrations, random clouds, dark security imagery, and fake dashboards that do not resemble the app.

## Technical Scope

This design does not require real-time multi-device conflict resolution for the first release.

The first implementation should support:

- Create encrypted backup.
- Upload encrypted snapshot.
- Detect existing cloud backup after login.
- Restore into empty or newly installed local SQLite.
- Manual refresh backup from Profile.
- Clear error states and recovery phrase warnings.

Out of scope for the first implementation:

- Real-time collaborative sync.
- Complex merge between two independently edited devices.
- Server-side readable contact records.
- Automatic restoration without recovery phrase.

## Risks and Decisions

- A 6-digit OTP-style code is not acceptable for encryption because it is too easy to brute force offline.
- A device-only key is not acceptable because it fails the phone-change use case.
- Server-side readable backup is simpler but weakens the privacy promise.
- The chosen compromise is account login plus generated recovery phrase.

If the user loses the recovery phrase, Recall People cannot decrypt the backup. The app must say this clearly, but briefly.

## Acceptance Criteria

- Onboarding clearly communicates the main value: useful profile, upcoming events calendar, conversation ideas, smart search, and privacy-led backup.
- Privacy details are still accessible from Profile.
- Encrypted backup is visible during onboarding and from Profile.
- Copy is available in English and French first, then mirrored to other app locales.
- Visual assets are generated or mocked in a consistent Recall style.
- The backup model is cross-platform for iOS and Android.
- Recall People stores only encrypted backup data and cannot decrypt contact content without the user's recovery phrase.
